# LIC1: Third-party source archives for GitHub Releases

This step settles the "Left for user review" items 1 and 3 from S12 and completes the release-side source
offer. The user approved all of these decisions. Not legal advice.

## Decisions implemented

1. **Source offer (S12 item 1).** The commitment stays as written: every Release attaches the
   corresponding source archives, and a missing one is provided on request through a GitHub issue.
   `THIRD_PARTY_NOTICES.md` §1 is final and explains each choice. §4 now says that SearXNG is unmodified
   (S12 item 2, settled by S11/H17).
2. **LGPL libiconv inside lxml (S12 item 3).** Releases also attach the lxml sdist and the libiconv
   sources.
3. **Other copyleft components.** `components.json` and the lock were reviewed. Nothing else needs an
   archive:
   - certifi (MPL-2.0) ships only in source form;
   - zstd is used under its BSD option;
   - libxml2, libxslt and zlib are permissive;
   - NSIS uses the zlib license;
   - everything else is PSF, MIT, BSD, Apache-2.0, ISC, Unicode, OFL or CC-BY.
4. **Release workflow.** It attaches every archive and lists them in the notes. The job runs in the
   `release` environment.

## Finding: the lxml notices named the wrong library versions

The S12 note took the lxml bundle versions from `buildlibxml.py`: libxml2 2.14.6, libxslt 1.1.43 and
libiconv 1.18. Those are the versions of the Linux and macOS static builds. The shipped Windows wheel is
`lxml-6.1.3-cp313-cp313-win_amd64.whl`, sha256 `e477aca0...2477`, the hash pinned in the lock. Its
`etree.cp313-win_amd64.pyd` is byte-identical to the vendored copy, and it reports these versions:

- `LIBXML_COMPILED_VERSION (2, 11, 9)`
- `LIBXSLT_COMPILED_VERSION (1, 1, 45)`
- `ICONV_COMPILED_VERSION (1, 17)`

On Windows, `buildlibxml.py` downloads the latest release of `lxml/libxml2-win-binaries`. The wheel was
uploaded on 2026-09-02, so that release was `2026.05.17`. It contains:

- `iconv-1.17.1`, built from the `winlibs/libiconv` submodule at `880a1fa8`, which is GNU libiconv 1.17
  with MSVC projects and `libiconv.patch`;
- `libxml2-2.11.9`;
- `libxslt-1.1.45`;
- `zlib-1.3.2`.

It is the only release that matches all three versions. The release before it, `2026.03.25`, has
libxslt 1.1.39.

These files were changed to match:

- `components.json` `extra_notices.lxml.bundles`;
- `packages.json` and the §7 table, regenerated by `gen_notices.py` against the hash-locked wheels;
- `licenses/bundled-in-wheels/libxml2-2.11.9-Copyright.txt`, the new name of the libxml2 notice. Its
  text is different in 2.11.9, and is now identical to GNOME `v2.11.9` and to the winlibs submodule;
- `libxslt-1.1.45-Copyright.txt`, the new name of the libxslt notice. Its text is unchanged, and
  identical to `v1.1.45`.

The zlib text was already correct.

## Release assets (`scripts/ci/third-party-sources.json`)

The file has a new schema: an `archives` list. Each entry has `id`, `name`, `version`, `license`,
`ships`, `url` + `sha256` (or `from_pins`), `asset` and `measured`. Every hash was measured on
2026-10-18 by downloading the file twice; both downloads were identical.

| Asset (`third-party-sources.` + …) | Source | SHA-256 | Cross-check |
|---|---|---|---|
| `AutoHotkey-v2.0.19-source.zip` | GitHub tag archive | `5baa09e9…cc4b` | unchanged from S14 |
| `searxng-6671d89…-source.tar.gz` | `build/pins.json` | `fabb3759…f980` | same tarball as the build |
| `lxml-6.1.3.tar.gz` | files.pythonhosted.org (PyPI sdist) | `45222d94…dd21` | equals the PyPI JSON digest |
| `libiconv-1.17.tar.gz` | ftp.gnu.org/gnu/libiconv | `8f74213b…1313` | `.sig` published next to it |
| `libiconv-winlibs-880a1fa8…-source.tar.gz` | GitHub commit archive | `89dd45d7…3eb6` | `iconv.h` `_LIBICONV_VERSION 0x0111` |
| `libxml2-win-binaries-2026.05.17-source.tar.gz` | GitHub tag archive | `ed1e5919…0813` | contains `build.ps1` and `libiconv.patch` |

There are two libiconv archives:

- The GNU tarball is the official upstream source at the bundled version.
- The winlibs tree is what the library was actually compiled from: GNU source, plus MSVC projects and a
  small patch.

The libxml2-win-binaries archive holds the scripts used to control compilation. GitHub archives
(codeload) are not promised byte-stable. As for the AutoHotkey entry: on a mismatch, re-verify the tree
and re-pin.

## `scripts/ci/get-sources.ps1`

- It now loops over `archives`. It checks:
  - asset names (plain, unique);
  - https URLs;
  - 64-hex pins;
  - the AutoHotkey version against `pins.json`;
  - the SearXNG commit against `pins.json`;
  - the lxml version against `build/requirements-searxng.txt` and `components.json`;
  - that `components.json` names `libiconv <version>`.
- It fails on unexpected files in `-Dest`.

## `.github/workflows/release.yml`

- The draft job has `environment: release`. **The coordinator must create the `release` environment
  in GitHub (Settings → Environments) and add required reviewers.** Until then, GitHub creates the
  environment automatically on the first run, with no protection rules.
- Staging requires the downloaded folder to match the asset list in `third-party-sources.json`
  exactly; it used to require exactly 2 files.
- The release notes list every `third-party-sources.<asset>` with its name, version and license,
  generated from the JSON. They repeat the "open an issue" offer.
- The actions stay pinned by SHA. No action was added.
